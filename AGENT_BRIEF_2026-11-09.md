## Задачи

### N1 (главная). Факториальная причинная проба «тот же полюс»

Цель: разделить два бага, которые сейчас неразличимы:
- **A — выбор (retrieval):** правильный полюс существует, но при парафразном cue выбирается
  неверный (плоская salience `min(5.0, …)`, выбор по монетке).
- **B — чтение эпизода:** полюс верный, но речевая голова не умеет его использовать
  (нужна рекуррентность/обучение readout).

Дизайн — 2×2, **с обязательными контролями**. Для обученной строки и для двух
незнакомых префиксов из T3:

| | полюс оригинального промпта (корректный) | полюс чужой семьи (неверный) |
|---|---|---|
| **дословный префикс** | A1 (ожидаем связно) | A2 (ожидаем не связно) |
| **парафразный префикс** | **B1 ← главная ячейка** | B2 (ожидаем не связно) |

Плюс контроль без подстановки полюса для обоих префиксов (C1, C2 — как сейчас в T3).

Процедура: определить полюс/эпизод, извлекаемый для оригинального промпта; подставить
**этот же** полюс в контекст парафразного префикса и продолжить teacher-forced. Для B2
подставить полюс из другого семейства (например, Beyoncé в запрос про Notre Dame).
Не обучать, не патчить production-путь, изоляция изменений обязательна.

Интерпретация (строго):

- **B1 связно, B2 не связно** ⇒ подстановка работает, полюс причина ⇒ баг **A (выбор)**.
  Направление правки: salience/маржа/cue-match в конкуренции CA3.
- **B1 не связно** ⇒ подстановка правильного полюса не помогает ⇒ баг **B (чтение
  эпизода)** либо полюс вообще не является причинной переменной. Направление правки:
  рекуррентность/prefix-state на токенном пути (w_ca3_seq) либо обучение readout.
- **B1 ≈ B2** ⇒ полюс не причинная переменная ⇒ декодер его не читает; это третья
  возможность, её надо назвать прямо, а не прятать под A или B.

Для каждой ячейки приложить: префикс, подставленный полюс (идентификатор), продолжение,
token IDs, позиция EOS, число токенов, вердикт связности по заранее записанному
критерию, grounding (измерительным гейтом, не runtime).

**Критерий связности должен быть записан ДО измерения** и не подгоняться под результат.

### N3. Два разных гейта: runtime-безопасность и измерительный

- **Runtime-гейт** (что модель отдаёт пользователю) — не трогать: строгая опора на
  источник, текущее поведение сохраняется байт-в-байт.
- **Измерительный гейт** — отдельная, явно помеченная функция/метрика, которая может
  принять семантически корректную перефразу, но обязана требовать доказательство
  (источник + правило матчинга + обоснование). Документировать, что гейт НЕ принимает.
  Используется только в диагностике/оценке.

Приёмка на корпусе T3: измерительный гейт **принимает** известные корректные
продолжения и **отвергает** бессвязные («all the the and texture had»). Если разделить
не удаётся — это результат, а не повод ослаблять правило.

Обязательные тесты: принимает корректную перефразу; отвергает мусор; отвергает
близкую, но неверную сущность (другая basilica / другая дата); runtime-путь даёт
идентичный вывод до и после (сравнение на фиксированной пробе).

## Правила отчётности

- Каждое число — с источником (файл + поле/ключ). Число без источника = дефект.
- Baseline и after рядом; если идентичны — писать это прямо.
- Никаких заголовков шире измеренного. «Порождение восстановлено» не писать, пока
  compose не измерен на невидимом контенте.
- Не переиспользовать старые ack/ссылки; любой вывод перепроверять на текущем коде.
- Пропущенный тест = дефект, а не «не применимо».
- Только чтение вне обучения: evaluation-контекст, фиксированный seed, состояние ядра и
  RNG восстановлено после каждого замера.
- Мастер не изменять, promotion не выполнять, acceptance/reference не читать в ходе
  train-пилотов. Новые файлы — только на D:.
- Каждая задача завершается результатом либо явным «не выполнено и почему».
