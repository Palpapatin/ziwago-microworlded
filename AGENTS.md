## 5. Аппаратные ограничения машины

RAM 15.9 ГБ, 8 физических / 16 логических ядер, GPU RTX 1660 Ti 6 ГБ
(делится с браузером). Пороги: VRAM ≤ 85 %, RAM ≤ 85 %, CPU ≤ 85 % ядер.

### 5.1 Тяжёлые процессы — только через `tools/limited_run.py`

Запуск без ограничения памяти приводит к OOM всей системы (включая чужую
работу пользователя). Правильный запуск:

```
python tools/limited_run.py --ram-pct 55 --cpu-pct 50 --log D:\...\run.log -- python <тяжёлый скрипт>
```

`limited_run.py` создаёт **Windows Job Object** с жёстким лимитом памяти
процесса (`JOB_OBJECT_LIMIT_JOB_MEMORY`) и жёстким потолком CPU
(`CPU_RATE_CONTROL_ENABLE_HARD_CAP`), запускает дочерний процесс
приостановленным, назначает его в job и только затем возобновляет. При
превышении лимита процесс получает `MemoryError` внутри себя и умирает, а
система остаётся живой. Проверено на контрасте: 200 МБ под лимитом 1 ГБ —
проходит, 2000 МБ — `MemoryError` внутри процесса.

Лимиты по умолчанию: 60 % RAM, 60 % CPU (переопределяются флагами или
переменными `ZIWAGO_RAM_PCT` / `ZIWAGO_CPU_PCT`). Для тяжёлых моделей —
50–55 %, чтобы оставить запас пользователю.

### 5.3 Профиль памяти загрузчика чекпоинта (измерено 2026-11-12)

* Чекпоинт 4.3 ГБ (fp32) **при загрузке даёт пик ~9.6–10.2 ГБ**: payload целиком
  поднимается в RAM, и восстановленное состояние — это вторая копия. Пик
  одинаков для рантаймов v19 и v20, то есть слой v20 память не добавляет.
* На машине с ~10 ГБ свободными это проходит впритык; при ~7 ГБ, занятых
  другими приложениями, загрузка упирается в потолок → OOM всей системы.
* `torch.load(..., mmap=True)` грузит в 2.3 раза быстрее (18.5 с против 43 с) и
  не поднимает чекпоинт в RAM целиком, **но восстановление после него падает с
  ACCESS_VIOLATION (0xC0000005)**: отображение на Windows доступно только для
  чтения, а модель пишет в веса на месте. В пути загрузки mmap не используется.
* Освобождение payload по мере восстановления (pop из снимка) снижает пик
  лишь на ~0.4 ГБ и ломает изоляцию снимка состояния для оценки — применять
  нельзя.
* Практический вывод: проверку v20-генерации запускать на машине, где
  свободно ≥10 ГБ, и обязательно через `tools/limited_run.py`.

### 5.4 Остальные правила машинного ресурса

* Тяжёлый прогон и pytest одновременно — убивают друг друга (на 8.8 ГБ под
  задачей свободно 0.6–1.1 ГБ — pytest убьёт обучение).
* Длинные процессы рантайм убивает через ~40 минут → запускать отсоединённо
  (`Start-Process cmd.exe -ArgumentList '/c', … -WindowStyle Hidden`) и не
  трогать машину до завершения.

## 8. Жизнь модуля: SHIPPED / PHANTOM / OFF / DEAD (2026-11-13)

Модуль считается частью организма, только если предъявляет ЧЕТЫРЕ вещи:

1. **владельца** — экземпляр, созданный организмом (точка `ClassName(` в `ziwago/`);
2. **вызов в живой фазе** — функция реально вызвана при обучении/генерации/сне
   (измеряется `tools/probes/module_map_probe.py`: `sys.setprofile` + граф объектов);
3. **измеримый эффект** — метрика, которая меняется при включении/выключении
   и **не является константой** (запрещено выдавать за метрику литеральную
   константу: `hippocampus.py:1120` `sequence_retrieval_accuracy = 0.96`);
4. **фантом-контроль** — тест, который выключает модуль и показывает, что
   метрика поехала.

Статусы: **SHIPPED** (все четыре пункта) / **PHANTOM** (создан, но не вызван) /
**OFF** (только под `*_enabled = False`) / **DEAD** (владельца нет).
Промежуточного состояния «написан, выключен, покрыт тестом» больше не существует.

Карта модулей: `MODULE_MAP_2026-11-13.md` + генерируемая таблица
`MODULE_MAP_TABLE_2026-11-13.md` (сборка: `tools/probes/build_module_map.py`).
Переход файла/механизма в DEAD/OFF — регресс, который виден в diff'е таблицы.

Измеренная база (13.11): файлов SHIPPED 26 (16 563 строки), DEAD 41 (9 183 строки);
механизмов SHIPPED 44, OFF 11, PHANTOM 2, DEAD 51. Девять флагов интегрированного
контура и ридеута выключены по умолчанию.

### 8.1 Два авто-ассерта против театра (дёшево, без тяжёлого прогона)

1. **Класс, объявленный живым, обязан иметь вызов своего метода из production-модуля.**
   Инструменты: `tools/probes/class_instantiation_map.py` (кто кого создаёт и под
   каким `if`) + `tools/probes/module_map_probe.py` (кто реально вызван).
2. **Флаг `*_enabled = False` ⇒ модуль либо удалён из пакета, либо помечен как
   архивный.** Сейчас все десять флагов выключены по умолчанию
   (`integrated.py:30,35,36,37,42`; `readout.py:110,118,128,136`;
   `flat.py:1211`; `content_form.py`), и это нигде не отражено ни в одном
   чекпоинт-гейте. Состояние «написан, выключен, покрыт тестом» запрещено.

Третье правило, обязательное для любой новой метрики: **значение, возвращаемое как
«измерение», не может быть константой** (образец: `hippocampus.py:1120`
`sequence_retrieval_accuracy = 0.96`). Измерение, которое нельзя изменить
выключателем, — не измерение.

Дифф `MODULE_MAP_TABLE_2026-11-13.md` — обязательная часть регрессии: переход
файла или механизма в DEAD/OFF/PHANTOM-EFFECT виден глазами.

### 8.2 Новое поле в живом объекте = миграция при восстановлении (15.11.2026)

Восстановление ставит только те поля, что были в снимке. Любое новое поле,
добавленное в живой объект ПОСЛЕ этого чекпоинта, в снимке отсутствует — и
модель падала три раза подряд, пока это не закрыли:

| Симптом | Причина | Закрыто |
|---|---|---|
| `AttributeError: 'CorticalColumn' object has no attribute 'astrocyte'` | трек O (14.11) добавил астроцит в колонку | ленивое создание `CorticalColumn._ensure_astrocyte()` |
| `ValueError: ach must be in [0.0, 2.0]` | в кандидате v19 `ach=11.56` при номинальном ~0.4; кламп был только в `update()`, не в restore | `NeuroChemistry.normalize_restored_state()` + отчёт |
| `ValueError: Invalid action context or evidence` | резонанс CA3 у обученной модели до 2.5 → `(1-resonance)*0.5` уходил в минус | `ZiwagoBiologicalSNNAssistant._action_evidence()` |

Правило: новое поле ⇒ (а) ленивое создание или (б) пункт в
`ZiwagoPureSynapticDialogueOrganismV14.apply_restore_migrations()` — единой
точке после восстановления, которая пишет ОТЧЁТ в `restore_migrations`.
Миграция без отчёта = «тихое» изменение поведения модели.

Рекомендация: любая правка, добавляющая поле живому объекту, обязана
проходить проверку восстановлением СТАРОГО чекпоинта
(`ziwago_v19_bankfixed_20261109.pt`) и генерацией — иначе модель молча
перестаёт отвечать.
